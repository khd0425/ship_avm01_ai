## 2. 요구사양서 자체의 확인 필요 사항 (Rev.1.0 반영 권고)

1. **문서 내 참조 오류**: 「제 12 장 변경관리」(§9.3, §10.3, §11.1)를 참조하지만 12장이 없고 변경관리는 11장. 「제 9 장 Open Issues」(§9.1 M1, §9.3)를 참조하지만 9장은 개발 일정. §7의 「제 10.3 항」·「제 10 장 일정」은 각각 9.3·9장을 가리키는 것으로 보임. → 특히 **"Open Issues 미확정 시 일정 순연" 조항은 목록이 없어 발동 조건이 불명확**.
2. **§3.3 수치의 해상도 근거**: RAW10 3.70 Gbps, RAW12 4.44 Gbps, RGBA 49.3 MB, 1.48 GB/s는 **4056×3040 (12.33 MP)** 에서 정확히 재현되며 4032×3040에서는 맞지 않음(3.68 Gbps / 49.0 MB). 기본값을 4056×3040으로 설정. 센서 확정 시 수정.
3. **§4.3 시차 수치**: 16.9 px/°(§3.2)로 계산하면 3 m·베이스라인 20 cm에서 약 **64 px**인데 문서는 38 px(10 cm → 19 px). 약 9.9 px/° 기준 값으로 보이므로 산출 근거 확인 필요. 결론(블렌딩은 PiP 우선)에는 영향 없음.
4. **FR-7.1 클래스 수** (최초 6종 제안: person·bollard·fender·quay_edge·small_vessel·buoy, 근거는 [ai_dataset_plan.md](ai_dataset_plan.md)): "6종"이라 쓰고 8개 명칭을 나열(끝에 쉼표), §1.2는 "6~10종". §8.3의 「FR-7.6」은 존재하지 않음. → 클래스 목록 확정 필요(현재 설정: 사람·계선주·방충재·안벽 경계·소형 선박·계류삭·부표·등대).
5. **FR-5.1 검수 기준** "기능 선택 시 FPS 낮아짐"은 합격 기준이 아님 → 안정화 ON 시 최소 fps(예: ≥25) 명시 권장.
6. **FR-4.2 "자료 B 우측 화면과 동일한 어안 보정 뷰"**: §1.2는 자료를 "핵심 개발 기술"과 "카메라 배치도"로 부르고 "자료 A/B" 정의가 없음. 직선 유지(원근) 뷰인지 원통형 뷰인지 확정 필요.
7. **PR-2(33 ms)·PR-1(30 fps)의 전제**: 엣지 디바이스가 "협의 후 결정"(착수 후 2주). AGX Orin과 Orin NX의 성능 차이가 크고, 12MP 3채널 입력은 카메라 인터페이스(§6 위험 요소)에 좌우됨. §3.3 단서(4K로 축소 또는 15 fps)를 **정량 기준으로** 미리 합의 권장.
8. **PR-4(±5 %)와 외재변수** — 아래 §3 참조. §1.2 핵심기술의 "외재변수 자동 캘리브레이션"에 대응하는 FR이 없음.

## 3. PR-4(Top-View ±5 %)에 대한 수치 검토

카메라 높이 10 m, 아래로 20° 기울인 장착을 가정하고, **추정한 장착 파라미터에 오차가 있을 때** 5/10/15 m 지점의 거리 오차를 계산(`geometry/view_math.hpp`):

| 장착 파라미터 오차 | 5 m | 10 m | 15 m |
|--------------------|----:|-----:|-----:|
| 피치 +0.25° | −1.1 % | −0.9 % | −0.9 % |
| 피치 +0.5° | −2.2 % | −1.7 % | −1.9 % |
| **피치 +1.0°** | **−4.3 %** | −3.4 % | −3.7 % |
| 피치 +2.0° | −8.6 % | −6.8 % | −7.2 % |
| **높이 +0.5 m** | +5.0 % | +5.0 % | +5.0 % |

- 픽셀 위치 오차 1 px은 0~15 m에서 최대 **0.49 %** (내부 캘리브레이션·해상도는 여유가 큼).
- **지배 요인은 설치 높이와 피치각**: 피치 오차 ≲1°, 높이 오차 ≲0.5 m(5 %) 이내여야 ±5 %가 가능. 발주처 설치 제원(§7 #6)의 정밀도 요구와, 현장 외재변수 교정 절차(기지 거리 표식 + `verify_calibration`)를 검수 절차에 포함하길 권장.
- 수평선 기반 피치/롤 자동 추정(§1.2)은 [O] 항목으로 협의하는 것이 좋음(현재 코드에는 없음).

## 4. 설계

### 4.1 Jetson 실행 구조 (CUDA + OpenCV)

```
 카메라 스레드 ×3 (EO, IR0, IR1)                         ← OpenCV VideoCapture (V4L2 / GStreamer), 시뮬레이터
   └ mapped pinned 메모리 링버퍼(3슬롯)  ── Jetson은 CPU/GPU가 같은 DRAM: 복사 없음 (zero-copy)
                     │ 최신 EO 프레임
 처리 스레드  ◄──────┘                                    (느리면 프레임을 건너뜀 = 최저 지연)
   ├ 시간 동기(EO 기준 16 ms) ─ IR AGC(히스토그램 LUT, 호스트)
   ├ [stream INFER]  LUT 리맵(정면 뷰) → 전처리 → 검출기(비동기)
   ├ [stream VIEW]   view 커널: 원본 어안 → 가상 카메라 뷰(프리셋/Top-View/안정화) RGBA
   │                 → IR PiP 합성 → AR 오버레이
   └ 출력 프레임(mapped RGBA) → 표시(OpenCV) / 녹화(NVENC, GStreamer)
```

- **CUDA**: 시점 렌더링, 리맵, PiP/AGC 합성, 전처리, AR(현재 코드). **OpenCV**: 카메라 입력(GStreamer 포함), 녹화, 화면 표시, 캘리브레이션 도구. JetPack 기본 OpenCV는 보통 CUDA 모듈(`cv::cuda`) 없이 빌드되어 있으므로 픽셀 단위 처리는 직접 작성한 CUDA 커널로 수행.
- 호스트 전용 `avm_host` 라이브러리(설정·기하·동기·AGC·프리셋·PiP·녹화 제어·로그·검증)는 CUDA/OpenCV 없이 어디서나 빌드·테스트됨. CUDA 커널은 **같은 헤더(`geometry/view_math.hpp`)** 를 `__host__ __device__`로 재사용하므로, 호스트 테스트가 커널의 수식을 그대로 검증함(float 커널 정밀도 대 double 차이 0.0002 px).

### 4.2 가상 카메라 모델 (FR-4·5의 핵심)

모든 화면은 "수면 위에 놓인 가상 핀홀 카메라"(위치·자세·화각)다. 출력 픽셀의 광선을 수면(y = 카메라 높이)과 교차시킨 뒤 실제 어안 카메라로 재투영한다.

- 전방 뷰 = 실제 카메라와 같은 위치의 가상 카메라(순수 회전).
- Top-View = 위에서 수직으로 내려다보는 가상 카메라 → **정확한 IPM**. 화면 높이 전체가 30 m(반경 15 m)에 대응하므로 스케일은 H/30 px/m (출력 360 px → 12 px/m, 1080 px → 36 px/m).
- 프리셋 전환 = 가상 카메라 포즈·화각 보간 → 급격한 점프 없음.
- 안정화 = 카메라 포즈에 IMU 자세 반영(가상 카메라는 수평 좌표계 기준이므로 화면이 수평 유지).
- 합성 어안 사진(수면 1 m 격자)으로 시각 검증: 원본에서 휘어진 격자가 전방 뷰에서 직선, Top-View에서 정사각형 격자(가로·세로 모두 12.000 px/m)로 나오며 10 m 기준선의 위치도 예상과 일치.
- 한계(사양서 §4.4 명시): 수면 평면 가정이므로 안벽·구조물은 바깥으로 늘어남.

### 4.3 Jetson/JetPack 관련 결정 사항

| 결정 | 이유 |
|------|------|
| 호스트 C++17, CUDA C++17 | JetPack 5: GCC 9.4(C++20 불완전), CUDA 11.4(nvcc C++17까지). JetPack 6에서도 동작 |
| CMake ≥ 3.18 | JetPack 5 기본 3.16은 업그레이드 필요 (`pip install cmake`) |
| `cudaHostAlloc(Mapped)` zero-copy | 통합 메모리 SoC에서 `cudaMalloc + cudaMemcpy` 이중 버퍼는 낭비 (사양서 zero-copy 요구) |
| `find_package(CUDAToolkit)` | 폐기된 `find_package(CUDA)` 대체 |
| **CMAKE_MODULE_PATH 설정 추가** | 기존 빌드는 `FindTensorRT.cmake`를 한 번도 로드하지 못해 **TensorRT가 항상 "not found"로 처리되고 있었음** |
| 시뮬레이션 카메라 기본 제공 | 카메라 하드웨어 도착(착수 후 3주) 전에도 전체 파이프라인·UI·녹화 개발 가능 |

## 5. 검증 현황 (정직한 구분)

**실제로 실행해서 확인한 것**
- 호스트 단위테스트 8개(CTest) 통과 (약 14,900 검사).
- **전체 애플리케이션을 이 PC에서 빌드·실행**: nvcc 12.9(sm_75) + OpenCV 4.13. 모든 `.cu`가 컴파일되고, TITAN RTX에서 30 fps·프레임당 연산 평균 2.5~3.5 ms(예산 33 ms)로 동작.
- **실제 USB 카메라**: icSpring 어안(EO 슬롯), Microsoft LifeCam(일반 화각, 창 0). 원본 어안 뷰·보정 전방 뷰·Top-View·ROI 확대·안정화(시뮬레이션 롤/피치)·PiP·AGC·"채널 비활성" 표시·녹화 파일 생성·로그 파일 확인.
- **AI**: COCO 부분집합으로 YOLOv8n 미세조정(25 에폭) → ONNX → C++ 디코더 → LifeCam 라이브 영상에서 `person` 검출. 표준 사진(bus, zidane)으로 디코딩 정확성 확인.
- PC 실행 중 발견·수정한 결함: IR 프레임을 "최신 1장"만 쓰던 동기 방식(EO 처리가 밀리면 IR이 2프레임 앞서 제외됨) → 히스토리에서 **가장 가까운 프레임 선택**으로 변경, 별도 GPU에서 mapped 메모리에 픽셀 단위로 쓰던 렌더 커널이 46 ms → **디바이스 버퍼 렌더 + 1회 복사로 0.3 ms**(프레임당 61 → 8 ms).

**이 PC에서 확인되지 않는 것 (Jetson 필요)**
- 통합 메모리 zero-copy 경로(PC는 별도 GPU라 스테이징 복사 경로로 동작), TensorRT, NVENC 녹화(PC는 소프트웨어 인코더로 대체됨), GMSL2 12MP 카메라, JetPack의 CUDA 11.4/GCC 9.4 빌드, 실제 성능(PR-1~6).
- 두 USB 카메라는 하드웨어 동기가 아니라 시간차가 커서 동기 허용 오차를 100 ms로 완화해 시연함(사양의 16 ms는 동기 카메라 전제).
- 데스크톱 데모 설정의 카메라 자세·어안 파라미터는 추정값(수평 90°/FOV 180° 가정) — 정확한 보정은 `calib_fisheye`로.
